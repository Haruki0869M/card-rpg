**今の作り（事実）**

### 1-4. ダンジョンへの合流（オーナーの決定 5-B・新しい設計）

**今の作り（事実）**
- ダンジョンの組は `Expedition`（`src/types/game.ts:441-453`: `id`・`heroes`・`mode`・`dungeon`・`battle`・`reward`・`chest`・`event`・`vote` …）。**組ごとに1つのダンジョン（部屋の並びと進み具合）を持ち、位置も組で1つ**（`DungeonRun.pos`）。キャラごとの位置はありません。
- 入り方: 世界マップの `interact` の `'dungeon'`（`world.ts:738-755`）→ 侵食度 +2% → 同行者を `w.acted` に入れる → `enterDungeonFromWorld`（新しいダンジョンを作る）→ `detachExpedition`（新しい組を `expeditions` に足し、世界マップの手番を進める）。
- 手番: 組は「その中の最初の生きているキャラの番」でまとめて動く（`advanceTurn` `world.ts:79-101`・`isExpeditionTurn` `:116`）。組の手番が終わると `endExpeditionTurn`（`:119-123`）で全員を行動済みにする。
- 場面の中の操作は `runInScene`（`game.ts:196-233`）が組を冒険に載せて処理する。投票の参加者 `voters` は `sceneHeroes`（＝その組の生きているキャラの担当）から毎回計算（`votes.ts:15`）。票の目印 `voteCtx`（`votes.ts:21`）に**人数は入っていない**。
- 戦闘の参加者は `sceneHeroes`（`game.ts:729`）。宝箱の取り合い・お金の山分けも場のキャラ。撤退で失う物は組の `dungeon.gained`。
- 世界マップの「〇〇に入る」ボタンは `WorldScreen.tsx:311`。手番でない組の人には「〇〇たちが△△を探索中です」（`:463`）。
- ランダムダンジョンは同じ id（例 `randomForest`）が地域ごとに置かれる（`generate.ts:135`）ので、**id だけでは「同じダンジョン」と決められない**。

**どう合流させるか（提案）**

| 項目 | 案 |
|---|---|
| 同じダンジョンの見分け方 | `Expedition` に **`entranceTile`（入口のマス番号）** を足し（省略できる項目）、`dungeon.dungeonId` と `entranceTile` が両方同じ組を「先行の組」とする。古い保存の組は `entranceTile` が無いので、`dungeonId` だけで（固定ダンジョン）・ランダムは合流しない |
| 合流の操作 | 新しい操作は作らず、`WORLD_INTERACT`（`'dungeon'`）の中で**先行の組があれば合流に分岐**。ボタンの文は「〇〇たちに合流する（翠の神殿）」。同行者（誘いを承知した他の人のキャラ）も一緒に合流（今の入り方と同じ決まり） |
| 合流する場所 | **先行の組の今の通路**（組の `heroes` に足すだけ。位置は組で1つなので、入口から別々に歩く形は作らない）。物語は「〇〇が追いついた！」のログ。入口に立ってから追いつくまでの演出は無し |
| 合流できる時 | 先行の組が **通路にいる時（`mode === 'dungeon'`）だけ**。戦闘・報酬・宝箱・イベント・休憩の途中、制覇後の帰還待ち（`cleared`）は「〇〇たちは今、戦闘中です。終わってから合流しよう」と断り、**手番は使わず侵食度も上がらない**（`interact` の最初で断るので、何も変わらない）。待ち行列（終わったら自動で合流）は作らない（保存の形と手番の扱いが増えるため。提案） |
| 侵食度・手番 | 合流も「ダンジョンに入る」ので **+2%**（今と同じ）。合流したキャラはその手番を終える（`w.acted` に入れ、`advanceTurn`）。組の手番の順番は `heroes` の先頭のまま（後から来た人は末尾） |
| 投票 | `voters` は `sceneHeroes` から毎回計算するので、合流した人は自動で投票に入る。**`voteCtx` に場の人数を足し、合流した瞬間に出しかけの票を無効にする**（半分だけ集まった票で決まらないように） |
| 戦闘・報酬・宝箱 | 次の戦闘から参加（`sceneHeroes`）。カード報酬・取り合い・山分けは今までどおり「場にいるキャラ」。合流前に組が手に入れた物（`gained`）はそのまま組の物 |
| 途中で抜ける | **できない**（撤退は組の投票で全員が出る。今と同じ）。「1人だけ戻る」は作らない（提案） |
| 深さ・敵のレベル | 先行の組のダンジョンのまま（部屋は入った時に決まっている）。合流した人のレベルが低くても補正しない（難易度は下げない） |

## 3. パート3: 戦闘の戦略性と演出

### 3-1. 直行 bot の基準

**今の作り（事実）**
- `straight: true`（`bot.ts:71-79`）が変えるのは世界マップの動きだけ（レベル上げをしない・次の鍵へ直行）。ダンジョンの中は普通の bot と同じで、**部屋の中身を知っていて**「HP半分未満なら休憩、そうでなければ宝箱、無ければ先頭の部屋」を選びます（`bot.ts:353-354`）。転職しない・お供を迎えない・手札は左から・フォーカスはほぼ使わない。
- 直近の測定（40行・52行の形）: 2人 15/28・4人 21/28 がクリア。

**どう変えるか**
- bot の扉の選び方を「予兆を見て選ぶ」に揃える（部屋の中身は読まず、予兆の色だけ。直行 bot は**いつも左端の扉**＝予兆を見ない。提案）。
- 基準: **直行 bot は2つ目の鍵のダンジョンで全滅する**（「2つ目の鍵のダンジョンの制覇率 20%以下・ふつう・2人と4人」を目安にする。提案）。合わせて「普通の bot（レベル上げをする）」も測り、**普通の bot のクリア率が 30〜50%**なら「ビルドと対処をした人が突破できる」の目安にする（提案。人は bot より強い）。
- 調整のつまみ（順に）: 深さの敵レベルの上がり方（§2-2）→ 強敵・中ボスの編成 → 敵の HP/攻撃の倍率（難易度の `levelBonus`）。**やさしくする方向には触らない。**

### 3-2. 敵の大技の予告を崩す（BREAK）

**今の作り（事実）**
- 予告は敵フェーズの終わりに決まり（`battle.ts:674` の `decideAllIntents`）、`enemy.intent = { actionId, targetId }`（`types/index.ts:506-509`）に入る。**「溜め」「大技」「全体攻撃」を表す種類やタグは無い**（`EnemyActionDef` は id・名前・効果だけ。`charge` は名前だけで中身は単体攻撃）。全体攻撃は効果の `to: 'foes'`。
- 予告を変える仕組みは2つある: 時間停止 `skipIntent`（次の1回を休み）、強奪 `stealIntent`（`nextActionMultiplier` を0.5にする。`battle.ts:719-721`）。**予告の枠の数字（`format.ts` の `intentView`）は `nextActionMultiplier` を掛けていない**ので、強奪で半分になっても枠の数字は変わらない（直す対象）。
- 完全成功なら属性の状態異常は**必ず付く**（`effects/index.ts:247` の `ctx.perfect ||`。氷→凍結=行動キャンセル、雷→痺れ=30%失敗、炎→火傷）。つまり依頼の「または、弱点属性の完全成功で状態異常が確定」は**ほぼ今も成り立っています**（弱点でなくても付く）。
- 敵のブロックを消す部品は無い（貫通 `ignoreBlock` はある）。弱点の倍率は 1.5（`elementWeakMul`）。予測は `predictCardTotals`（`battle.ts:522-560`。本物の処理を複製で試す）。

**どう変えるか（提案・おすすめ: 「大技」の印＋BREAK）**
- **データ**: `EnemyActionDef` に `big?: true`（大技・全体攻撃の予告）を足し、強敵・中ボス・ボスの大技に付ける（敵約230体のうち、強敵・ボスの大技だけ。データの追加作業）。
- **BREAK の決まり**: 敵が `big` の予告を出しているターンに、味方が次のどれかを達成すると **⚡BREAK!**:
  1. **弱点属性でダメージ**を与えた
  2. **完全成功**で攻撃を当てた
  3. そのターンの**合計ダメージが敵の最大HPの 20% 以上**（提案の値）
  効果: **予告の威力が半分**（`nextActionMultiplier = 0.5`。強奪と同じ流れ）＋**弱体1**＋**ブロック0**。1つの予告に1回。
- 理由: 依頼の3つの「または」のうち、(1)威力を下げる と (2)BREAK（弱体＋ブロック解除）を**1つの出来事にまとめる**と、覚える決まりが1つで済み、予測欄に出しやすい。(3)の状態異常の確定は今すでにあるので、**予測欄に「❄️完全成功で凍結（敵の行動を止める！）」と大きく出す**だけで依頼を満たせます。
- **予測欄**: `TargetChips` の文に「⚡ この攻撃で BREAK（大技 48→24）」「❄️ 完全成功で凍結」を足す。`intentView` に `nextActionMultiplier` を反映（強奪の表示も直る）。敵の予告の枠に大技の印（🔥）と、BREAK 後は「体勢が崩れた」の表示。
- 実装の場所: `effects/index.ts` の `dealDamage`（191行付近）で条件を判定し `breakEnemy()` を呼ぶ。状態 `enemy.broken?: boolean`（戦闘の中だけの省略できる項目）。演出は `presentation.ts` に `break` のコマ（技名の帯と同じ赤→金の帯「BREAK!」）。

**危ない所**
- 乱数は使わない。保存は省略できる項目だけ（版は上げない）。オンラインは同じコマンドから同じ結果。
- 時間停止・強奪との重なり: 両方かかった時は「休み」が優先（今の処理順どおり）。
- `battle.test.ts`・`jobs.test.ts:378-412`（nextActionMultiplier）に BREAK のテストを足す。

手間: **中**（エンジンは小さいが、大技の印のデータ付けと予測欄の表示に手間）。

### 3-4. 攻撃が当たった瞬間の演出が実機で見えない

**今の作り（事実）**
- 命中の演出は `ImpactLayer`（`BattleFx.tsx:217-228`、`absolute inset-0 z-[25]`）で、**敵の立ち絵の `motion.div` の子**（`Battlefield.tsx:293`）。時間は `impactFx 0.42秒`・白フラッシュ `0.12秒`・揺れ `0.12秒`（高速モードは半分）。
- 出す条件は「HPが実際に減った時」だけ（`presentation.ts:129`）。コマが48を超えると全部一度に出る（`battleStore.ts:510`）。
- 頭上のスロット枠 `SlotOverlay` は戦場の上から 46%・`z-40`・黒80%（`Battlefield.tsx:559`）で、結果の表示（0.6秒）を含めてスロットの後も残る。敵の予告の枠は高さ 40〜55% あたり（推測）。失敗「✖」の枠は暗い赤（`SlotOverlay.tsx:13`）、フォーカス「★」の光は `box-shadow` が**止まったまま**（`battleFx.css:176`）。
- 動きを減らす条件: OS の `prefers-reduced-motion`（**Android の「アニメーションを削除」で Chrome も reduce になる**）か、ゲームの「簡易」。その時は火花・粒・フラッシュ・揺れが出ず、形だけ薄く出る。

**原因の候補（推測。実機で確かめて絞る）**
1. **スロットの黒い板（z-40）が、命中の演出（z-25）の上に、演出の間ずっと乗っている**。命中はスロットが止まった時刻に始まり、板は結果の表示 0.6秒ぶん残る。敵の立ち絵の高さによっては完全に隠れる。
2. **短すぎる**: フラッシュ 0.12秒・揺れ 0.12秒は、端末が重いと1〜3コマで終わる。
3. **Android の reduce 設定**で calm になり、ほぼ出なくなる。
4. とどめの一撃: 演出が倒れる敵の `motion.div` の子なので、**敵と一緒に薄くなる**。
5. GPU 合成: `will-change: transform` の層の親に `filter: brightness` をかける・`mix-blend-mode: screen`・`backdrop-filter`・SVG の `drop-shadow` の組み合わせは、Android で消えたりちらついたりする典型。
6. 全部ブロックされた時は演出が無い（仕様どおりだが、見えないと感じる原因の1つ）。

**どう変えるか**
- **実装の最初に実機で確定する**: `scripts/battle-fx-frames.mjs`（新規。0.05秒おきに撮る）で「板が重なっているか」「演出が何コマ出ているか」を数え、**オーナーの実機の動画（コマ送り）と見比べる**。原因が分かるまで大きく作り替えない。
- 候補への直し（提案）:
  1. **スロットの板を戦場の中央から、手札の上の帯へ移す**（高さの 46% → 下端の細い帯）。または結果が出たら即座に小さくする。敵の予告の文字とも重ならなくなる（依頼の「頭上スロット枠が敵の予告と重ならないように」もこれで解決）。
  2. 命中の演出を**敵の立ち絵の外（戦場の直下の専用の層、`z-[35]`）**に出す（倒れる敵と一緒に消えない・重なり順の問題が消える）。
  3. 時間: フラッシュ 0.12 → **0.18秒**、揺れ 0.12 → **0.16秒**、命中 0.42 → **0.5秒**（提案。高速モードは半分のまま）。
  4. 白フラッシュは `filter: brightness` ではなく**白い半透明の層を重ねて消す**（GPU の相性の問題を避ける）。
  5. **reduce の時も「最低限の形」は残す**（斬撃の線・魔法陣・白い層は出し、火花と揺れだけ止める）。設定画面に「端末の『アニメーションを削除』が有効です」の注意を出す（提案）。
  6. 失敗「✖」: 枠を明るい赤（`#ff4d6d`）＋赤い光、文字を白に。フォーカス「★」: 金の光を**脈打つ**アニメーション（calm では止める）。
  7. HPバーの白い残像（`HpBar.tsx:41`）は CSS だけなので、見えないなら色を白→薄い黄色の帯にし、保持 0.35 → 0.45秒（提案）。
- 確認: `stepb-battle.mjs`・`battle-feedback.mjs`・`enemy-turn-timing.mjs`・`check-layout.mjs`、新しい `battle-fx-frames.mjs`、fps（`perf.mjs`）。**最後はオーナーの実機で動画を撮ってもらい、見えるかを確かめる。**

手間: **中**（原因の確定に時間がかかる可能性）。

### 4-2. 乱数の順番
- ダンジョンのサイコロを引かなくなる・行数が変わる・ランダムダンジョンの偏り防止、で**ダンジョンの乱数の流れは全部変わります**。自動プレイの数字（クリア率・時間）は過去と比べられないので、**新しい形どうしで前後を比べる**（§6）。
