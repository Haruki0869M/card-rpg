# 賢いマルチプレイ検証 bot の細かい計画（区切り0・2026-11-17）

骨組み `docs/tasks/smart-coop-bot-plan.md`（オーナーの返事 = 全てA）を、今のコードと台本を読んで「作れる形」にした物です。
**この文書は計画だけ**（コードは変えていません。テスト・ビルド・ブラウザも流していません）。次は「別の目の憲章点検」→ 区切り1。

- 【提案】と書いた所は、骨組みに無くて、この計画で決めた物です。
- 【未確認】と書いた所は、コードを読んだだけで、動かして確かめていない見立てです（区切り1・4で測ります）。

## 0. 結論（先に）

1. **作れます。** 今の台本に、部屋を作る手順・押す前のかぶさり検査・地図を動かす工夫・はみ出しの点検がもうあり、土台の6〜7割は「集めて共通の部品にする」作業です。
2. **ゲームの側に足す物は「見えない印」が中心**です。印（`data-` の属性）を約80個（24ファイル）。見た目・動き・乱数は変えません。ほかに、確認用の入口（エミュレーターの時だけ読まれる）に2つ【提案】: 「種を決める」「取り直しの記録を読む」。
3. **頭（判断）は画面だけを見ます。** 確認用の入口 `window.__online` は「審判」だけが**読むだけ**に使い、通しの間は「送る・差し込む」を台本の側で封じます（§2-4）。
4. **時間は骨組みの見込みより長くなりそうです【未確認】。** 画面のボタンを1つずつ検査して押すので、2人の通しで 1.5〜2.5時間、4人で 3〜5時間の見立て。シナリオ1本（2人＋4人）は「夜に1本ずつ流す」運用になります（§8）。
5. **作る前に直す物が1つ**: 重い確認の順番待ち `heavy.mjs` は、30分より古い枠を「落ちたセッションの残り」として捨てます（`heavy.mjs:13,24`）。bot の通しは30分を超えるので、流している最中に枠を取られ、ほかの重い確認が同時に動いてしまいます。枠の時刻を書き直す小さな直しが要ります（§8-4）。
6. **オーナーに聞く事は3つ**（§10。どれも A がおすすめ）。

## 2. 土台

### 2-1. 端末を立てる
- ブラウザは1つ（`chromium.launch()`）、端末ごとに別の context（別の人として入る。`coop-agree.mjs:42-48` と同じ）。
- 画面の大きさ（骨組み §1 のとおり）: 2人 = P1 390×844・**P2 390×540**。4人 = ＋P3 360×640・P4 412×860。
- どの端末も `hasTouch: true, isMobile: true`（`adventure.mjs:147` と同じ）・`deviceScaleFactor: 1`（メモリを抑える）。押すのは**タップ**（指と同じ道）。
- 設定は先に入れる: 高速・振動なし・最初の案内なし・見取り図の案内なし。
- つなぐ先は `?emu=127.0.0.1` だけ。URL に本番の名前があれば止まる。`?emu=` が無くても止まる。

### 2-2. 部屋を作って入る・キャラを作る（全部画面のボタン）
1. P1: タイトル「新しい冒険」→（1本目以外のシナリオは、シナリオのカード）→「やさしい」→ 人数 →「オンライン協力」→ 名前 →「部屋を作る」→ 合言葉（`data-testid="room-code"`）を画面から読む。
2. P2〜: 招待のリンク（`&room=合言葉`）で開く → 名前 →「参加する」。【提案】4人の時、P4 だけは合言葉を手で打って入る（`OnlineScreens.tsx:89` の入力欄。招待リンクと手打ちの両方の道を通す）。
3. 1人1キャラ:「作る」→ ジョブを選ぶ →「このキャラに決める」。ジョブは種から決まる順で選ぶ（回復役を1人は入れる。通しごとに違うジョブを通すため）。
4. P1「冒険に出発」→ 全端末が世界マップになるまで待つ → 物語を閉じる（「タップで続ける」「つづける」）。
- 1本目以外のシナリオの解放は、`adventure.mjs:158-162` と同じく、始める前に伝承の書の記録を入れる（用意の時だけ。画面の操作の前）。

### 2-3. 全端末の「今の画面」を読む共通の形
`view.mjs` は、端末ごとに `page.evaluate` を1回だけ流して、次の形を返します（DOM の字と印だけ）。

```
View = {
  seat, viewport,     // P2・390×540 など（台本が知っている事）
  screen,             // title / setup / create / join / lobby / game
  mode,               // world / town / shrine / sanctuary / encounter / dungeon / battle / reward / chest / event / rest / cleared / ending / gameover
  sceneTab,           // 今見ている場面のタブ・「操作を待っています」の赤い点があるタブ
  layers: [...],      // 上に開いている物（シート・カード選び・説明の窓・確認の窓・見取り図・状態の一覧・遊び方）
  busy,               // 演出中か（歩き・戦闘の見せ方・スロット・サイコロ・扉・技名・宝箱の映像）
  waits: [...],       // 待ちの印（待ちの帯・「選んでいます」・票の枠・通信の知らせ）と、その字
  actions: [...],     // 今この端末で押せる物（印・字・押せる状態か）
  facts: {...},       // 場面ごとの読み取り（§4 の表）
  sig                 // 画面の指紋（screen＋mode＋layers＋押せる物の一覧を短くした字）。止まりの検出に使う
}
```

画面の種類は、いちばん外の `data-app-root`（`src/App.tsx:277`）に足す `data-screen`・`data-mode`・`data-scene` で決めます（今は印が無く、字で見分けるしかない）。

### 2-4. 状態の印（指紋）の比べ方と、「読むだけ」の線引き

**決まり: 頭は DOM だけ。確認用の入口は審判だけが読む。通しの間は、書く入口を使えなくする。**

| `window.__online` の入口 | 通しの間 | 「場面から」の用意の時 |
|---|---|---|
| `hash`・`seq`・`isHost`・`seat`・`myPlayers`・`mode`・`ui`・`pins`・`seatOnline`・（足す）`resyncLog` | **審判だけが読む**（比べる・失敗の時に保存する） | 同じ |
| `game`・`full`（状態の写し） | **失敗の時の保存と、節目の保存（§6-3）にだけ**使う。頭には渡さない | 写しを元に用意する |
| `send`・`next`・`inject`・`resync`・`setProxy`・`goOffline`・`goOnline`・`stamp`・`openSheet`・`beforeRoom` | **使わない** | `inject`・`resync`・`beforeRoom` だけ（始める前） |

守り方（台本の作りで守る）:
1. `window.__online` と書いてよいファイルは `judge.mjs` と `scenes.mjs` だけ。`selftest.mjs` が、ほかのファイルに `__online`・`dispatch`・`.send(` が無い事を字で確かめる。
2. 用意が終わったら、審判が各端末で「書く入口」を、呼ぶとエラーになる物に差し替える（読み込み直しの後も、もう1度）。通しの途中でだれかが呼べば、その場で失敗になる。
3. 頭の関数は `View` だけを受け取る（ページを直接さわれない形にする）。

状態の印の比べ方:
- 押した後（と、少なくとも5秒ごと）に、全端末の `seq` がそろうまで待つ（上限15秒。敵の番はホストが自動で進めるので、そろった時に比べる。`online.mjs:144` と同じ考え）。そろったら `hash` を比べる。違えば「同期のずれ」。そろわなければ「追いつかない」。
- **取り直しの記録**【提案・足す入口】: 部屋は、ずれ（`hash`）・通らない操作（`error`）・抜け（`gap`）を見つけると自分で取り直す（`room.ts:130,622-648,702-703`）。これを数えないと、「ずれたが自動で直った」を見逃す。`onlineDebug.ts` に「取り直しの理由と番号を覚えておき、読むだけの `resyncLog()`」を足し、読み込み直しの直後（`join`・`start`）以外の取り直しは「同期のずれ」に数える。
- **見た目の同期**【提案】: 状態が同じでも、画面が古いままの不具合がある（書き直しの抜け）。同じ場面を見ている端末どうしで、DOM から読んだ事（場面の種類・仲間の HP・侵食度・手番の人）も比べる。

### 2-5. 画面に足す `data-` の印の一覧

決まり: **見た目・動き・乱数を変えない印だけ**（属性を足すだけ。要素は増やさない）。字で押せて、字が変わりにくい所（タイトル・待合室・「冒険に出発」など）は足さない。今ある印（576種類）で足りる所は足さない。作業者は、足す前に「もう同じ意味の印が無いか」を確かめる。

## 3. センサー（押す前の検査）

### 3-1. 押すまでの流れ（毎回）
1. **演出が終わるのを待つ**: `data-battle-presenting`・`data-world-moving`・`data-move-blocker`・`data-slot-overlay`・`data-dice-overlay`・`data-door-opening`・`data-dungeon-controls="busy"`・`data-turn-cutin`・`data-ability-cutin`・`data-chest-video`・`data-pet-reveal` のどれかがある間は押さない（上限20秒。超えたら「止まり」）。
2. **スクロールの中なら見える所へ**: 押す物が、スクロールできる窓の中で見えていなければ、その窓の中だけをスクロールする（人が指で送るのと同じ。記録に残す）。
3. **止まるのを待つ**: 押す物の四角を80ミリ秒あけて2回測り、同じになるまで待つ（シートがせり上がる途中で測らない。上限1.5秒）。
4. **3つの検査**（下）。当たったら 0.4秒あけてもう1度だけ測る。消えていれば「一瞬の当たり」として記録（失敗にしないが報告に出す。同じ所で3回起きたら、人が見る物として報告の上に出す）。残っていれば失敗。
5. **タップ**（検査した点を押す）。
6. **効いたかを確かめる**: 3秒以内に、その端末の画面の指紋か、全体の番号（seq）が変われば良い。変わらなければ「押しても変わらない」として数える（§3-5 の止まりに入る）。

### 3-2. 検査①: かぶさり
- **(a) 押せないかぶさり**: 押す物の四角（画面と、親のスクロールの窓で切った、見えている部分）に 3×3 の9点を取り、`elementFromPoint` で一番上の要素を調べる。**真ん中の点が、その物（か、その中の要素）でなければ失敗。** 9点のうち6点以上がその物でなければ失敗（半分以上が隠れている）。
- **(b) 見た目のかぶさり**【提案】: `elementFromPoint` は「押しても通り抜ける飾り」（`pointer-events: none`）を見ない。押せるが字が隠れて読めない、を見つけるため、下の「帯と覆いの一覧」の四角が、押す物の面積の 25% 以上に重なっていれば失敗。
  - 一覧: `data-turn-lock`・`data-online-overlay` の中身・`data-vote-status`・`data-wait-notes`・`data-pin-banner`・`data-tile-info`・`data-toast`・`data-callout`・`data-hidden-notice`・`data-challenge-wait`・`data-dungeon-wait`・`data-buy-notice`・`data-region-banner`・`data-dungeon-bar`（フッター）・`data-world-panel`。
- **例外（わざと重ねてある物）**:

| 場面 | 扱い |
|---|---|
| 押す物が、その帯・覆いの中にある（帯のボタンを押す） | 当たりにしない |
| 背景の暗幕を押して閉じる（`data-detail-backdrop`・`data-scourge-backdrop`・`data-status-list-backdrop`） | 暗幕そのものが押す物なので当たりにしない |
| 手札のカード（わざと重ねて並べる。選んだカードは大きくなって隣に乗る＝`data-hand-covered`） | 真ん中ではなく「見えている左の帯」（幅 43.5px 以上。`lib.mjs:103-108` の決まり）を押し、そこだけを検査する |
| 世界マップのマス（`data-reach`）の上の駒・お供・徘徊する敵・札 | 地図の中の物（`data-world-map` の中）なら当たりにしない（地図がタップを受ける）。地図の外の物（下のパネル・右のボタン・マスの説明の帯）が乗っていたら、**失敗ではなく地図を動かす**（`adventure.mjs:317-358` と同じ。動かした回数と理由を数える）。4回動かしても出せなければ失敗 |
| 短いお知らせ（Toast。数秒で消える） | 消えるまで待ってから測り直す（上限3秒）。残れば当たり |
| 演出中の覆い（3-1 の1） | 押さずに待つので、検査しない |
| ドラッグ中（地図をつまんで動かしている途中） | bot は地図を「その場でスクロール」で動かし、指のドラッグはしない。動かした直後は 3-1 の3（止まるのを待つ）で測り直す |

- **待ちの帯（`data-turn-lock`。画面の下 34%）は例外にしない。** 手番でない人が押してよい物（装備・道具のボタン、シートの×、ピン、票）に帯が乗っていたら失敗（実機の不具合②の形）。手番の人しか押せない物は、頭が選ばない。

### 3-3. 検査②: 窓の潰れ
毎ステップ、開いている窓（下の一覧）ごとに測ります（押す時だけでなく、開いている間ずっと）。
- 一覧: `data-sheet-body`・`data-card-pick-panel`・`data-item-pick-panel`・`data-detail-popup`・`data-event-panel`・`data-event-scroll`・`data-town-body`・`data-reward-scroll`・`data-claim-area`・`data-relic-picker`・`data-job-pick`・`data-hero-task`・`data-flotsam-options`・`data-status-list-body`・`data-help`・`data-scourge-dialog`・`data-opener-picker`。
- 式（窓の中の、縦にスクロールする箱について。見えている高さ = 箱の高さを画面で切った物）:
  - **中身がスクロールしないと読めない（`scrollHeight > clientHeight + 1`）のに、見えている高さが 150px 未満** → 失敗。
  - **見えている高さが 44px 未満**（ボタン1つ分も無い）→ 失敗。
  - **窓の四角が画面の外に出ている**（上が 0 より上・下が画面の高さより下）→ 失敗。
  - 中身が全部入っている短い窓（確認の窓など）は、150px 未満でも当たりにしない【提案。骨組みの「150px 未満」を「スクロールが要るのに 150px 未満」と読みました】。
- **要る要素が描かれているか**（ある・大きさが0でない・その窓のスクロールで届く）:

| 窓 | 要る要素 |
|---|---|
| どのシートも | ×（`data-sheet-close`）が画面の中で、押せる |
| パーティ・装備 | 装備の欄（`data-equip-slot`）が全部の種類ぶん・持ち物の列（`data-party-items`） |
| 道具袋 | 持ち物の行（`data-item-row`）ごとに「使う」（`data-row-use`）か「渡す」（`data-row-give`）。開いた行の枠（`data-row-panel`）が、行のすぐ下に見える |
| カード選び | 説明の文（`data-card-summary`）が空でない・「このカードを選ぶ」（`data-card-pick-action`）が画面の中 |
| 転職のカード選び | カード（`data-pick-card`）が1枚以上・下の案内（`data-job-pick-peek`） |
| イベント | 本文（`data-event-window`）が空でない・選択肢（`data-event-option`）が1つ以上。挑む段は「挑戦する」か待ちの字 |
| 報酬 | 下のボタンの段（`data-reward-bottom`）が画面の中 |

### 3-4. 検査③: はみ出し
- **横スクロール**: ページ全体の幅が画面より広い（`layoutIssues` の最初の検査）。毎回。
- **画面の外のボタン**: スクロールの窓の中でないのに、画面の外にあるボタン・カード・敵・味方（`lib.mjs:91-96`）。毎回。
- **字の見切れ**【足す検査】: 字のある要素で、中身の幅・高さが箱より大きく（`scrollWidth > clientWidth + 1` など）、はみ出しを隠している時。**「…」で切る決まりの所（`truncate`・`line-clamp`）は当たりにせず、数だけ数える**（わざと切っている。多すぎる場面は報告に出す）。ボタンが、スクロールしない親の箱で 2px より多く切れている時も当たり。
- **12px 未満の字・43.5px 未満のボタン**: `lib.mjs:97-121` のまま。
- 重い検査（字の見切れ・12px・小さいボタン）は、**その端末でその画面の指紋を初めて見た時だけ**流す（毎回は流さない。時間を抑える）。同じ当たりは「端末の大きさ＋画面の種類＋文」で1つにまとめる。

### 3-5. 止まりの検出
- **進んだ印**: 全端末の番号（seq）の最大が増えた／どれかの端末の画面の指紋が変わった。
- **止まり**: 演出中でないのに、進んだ印が **40秒** 無い。
- **互いに待つ**: どの端末の頭も「押す物が無い（待つ）」と答え、演出中でもない状態が **12秒** 続く → すぐ失敗（40秒待たない）。その時の各端末の待ちの字（「〜さんが選んでいます」など）を保存する。祠の行き止まり・報酬の待ち・漂流物の山の形がこれ。
- **同じ操作の繰り返し**: 同じ端末が、同じ画面の指紋で同じ物を8回押しても番号が進まない → 別の候補を1回試し、だめなら失敗（「押しても変わらない」の元の不具合の形）。
- **上限**: 2人 = 180分・4人 = 300分（測ってから直す）。超えたら「時間切れ」として、そこまでの網羅の表と一緒に報告。
- 秒数（40秒・12秒・8回）は【提案】。PC が重い時に誤って当たらないか、区切り1で確かめて直す。

### 3-6. 失敗した時に残す物
`screenshots/smart-coop/<シナリオ>-<人数>p-<種>/fail-<番号>-<種類>/` に:
- 全端末の写真（`P1.png`〜）・全端末の画面の中身（`P1.html` = DOM 全部・`P1.txt` = 見えている字）
- 全端末の `View`（`view.json`）・直前の操作の記録 50件（`actions.json`。だれが・いつ・何を・検査の結果）
- 状態の印（`sync.json`: 全端末の seq・hash・ホストか・席・`ui()`・取り直しの記録・ピン）・全端末の状態の写し（`state-P1.json`〜。審判が読むだけ）
- 画面のエラーと console の error の記録

**失敗した後**【提案・§10 の質問1】: 証拠を保存して、進められる限り続ける（最後は必ず「失敗」と報告。別々の種類が10個になったら止める）。1回の通しが長いので、1つ目で止めると、後ろの不具合を見つけるのに何回も流す事になるため。

### 3-7. 見逃しと誤検知を減らす工夫
- **自己テスト**（`selftest.mjs`。ゲームもエミュレーターも要らない軽い確認）: わざと作った小さな HTML（かぶさり・通り抜ける飾りのかぶさり・潰れた窓・横スクロール・字の見切れ・11px の字と、それぞれの「正しい形」）で、当たる物に当たり、当たらない物に当たらない事を確かめる。センサーを直すたびに流す。
- **実機の不具合5つ＋祠を、名前を付けた確かめにする**: 通しの中で、①イベントの2段階の合意 ②狭い画面のシート ③待ち中に「通信が切れています」が出ない ④取り合いとカード3択の順 ⑤転職のカード選び ⑥祠で片方が先に終わる、を踏んだ時に、専用の確かめを流す（網羅の表の行にする）。
- 誤検知は「例外の表」（3-2）に足して直す。**例外を足す時は、理由を1行書く**（何でも例外にして通す、をしない）。

## 4. 頭（場面ごとの判断の決まり）

共通の決まり:
- **見るのは `View`（DOM の字と印）と、台本が読んだゲームの説明書き（カード・装備・敵の決まった中身）だけ。** これから出る乱数・霧の中・まだ入っていない部屋は見ない。

- 判断の手本は `src/engine/botClever.ts`・`botSmart.ts`（数字の目安はそのまま借りる。下の表の「手本」）。エンジンの関数は呼ばない。
- 仲間どうしの相談（どの敵を狙うか・だれが開けるか）は、台本の中の「相談の板」で決める（人が声で相談するのと同じ）。

- 下の数字（HP 6割・80% など）は bot の作戦の【提案】で、ゲームの中身ではない。

## 5. 揺さぶり

### 5-1. 順番の決め方（確率を使わない）
- 揺さぶりの種類ごとに「機会」を数える（例: 扉の合意待ちが来るたびに +1）。**k 回目の機会で揺さぶるかは、「k を周期で割った余り = 種から決めた数」で決める。** 例: 周期3なら、3回に1回。どの回かは種で決まる。
- 押すのはいつも1台ずつ・全端末が落ち着いてから（§4）なので、同じ種なら同じ順番になる。
- 揺さぶりの間も、押す前の検査は全部流す。揺さぶりで使う操作も全部画面のボタン。

### 6-2. 通しで踏めなかった物
- 通しの終わりに、踏めなかった行を一覧にする → その行だけを「場面から」で踏む（下）。
- 「場面から」でも踏めない行があれば、合格にしない。

### 6-3. 「場面から」の保存の用意
- **基本は「通しの節目で取った保存」を使う**【提案】。通しの間、審判が節目（ダンジョンの制覇・町を出た時・転職の直前）ごとに、状態の写し（`__online.game()`。読むだけ）を `checkpoints/<シナリオ>-<人数>p-<節目>.json` に保存する。手で作った状態より、本当に起きる状態に近い。途中で落ちた時の「続きから」にも使える。
- 用意の手順（確認用の入口を使うのは、ここだけ）:
  1. 新しい部屋を、画面のボタンで作る（§2-2。人数と席は保存と同じ）。
  2. ホストが保存を差し込む（`inject`）→ ほかの端末が取り直す（`resync`）。
  3. 書く入口を封じる（§2-4）。**ここから先は全部画面のボタン。**
- 節目の保存では届かない場面は、保存に小さな書き換えを足す（書き換えた中身は、報告に必ず書く）:

| 場面 | 書き換え |
|---|---|
| 最上位・特殊への転職・決め技 | レベルと条件の数を満たす・神殿か祭壇の隣のマスに立たせる（転職の数字は `gameData.mjs` の `loadJobData` で読む） |
| 災厄（3体目まで） | 災厄のいるマスの隣に立たせる・HP を満タンに |
| ランダムダンジョンの奥の箱・封魔・漂流物の山・凍え | その部屋の扉の前まで進めた写し（`beforeRoom`。`onlineDebug.ts:63`） |
| 最後のダンジョン・エンディング | 鍵を全部持たせて、入口の隣に |
| 潮の2つの向き | 時間帯を変える |
| 依頼の報告 | 依頼の進み具合を満たす |
| 全滅からの立て直し・ゲームオーバー | HP を1に・命の灯火を0に |

- 【未確認】別の部屋で取った保存を、新しい部屋に差し込んで動くか（キャラの持ち主は席で決まるので動く見立て。今の `coop-*.mjs` は「その部屋の状態を書き換えて差し込む」だけ）。区切り4の最初に確かめる。だめなら「その部屋の最初の状態に、保存の中身を写す」形にする。

## 10. 心配な所と、作る前に決める事

### 10-1. オーナーに聞く事（3つ。どれも A がおすすめ）
1. **失敗を見つけた後**: A【おすすめ】= 写真と記録を保存して、進められる限り続ける（最後は必ず「失敗」と報告。10種類で止める）／B = 最初の1つで止める。

### 10-3. 憲章 §4 のチェック（どの作業でも）
- [x] **人が遊んで「濃い・楽しい・悩む」になるか**: bot は確認の道具で、遊びの中身は変えない。憲章7（2人で遊んで、押せない所・止まる所が無い）を、通しで遊ぶ中で見つけるための物。
- [x] **数字を水増しやコピーで満たしていないか**: 合格の線に「bot が勝つ」を入れない（憲章4・骨組み §5）。ゲームの数字は動かさない。戦闘の数・負けた場所は記録だけ。
- [x] **2人で遊ぶ時に、止まらない・押せない所が無いか**: それを毎回確かめる道具。足す印は見えず、新しい画面・操作は足さない。`&seed=` はエミュレーターの時だけ。
- カード・装備・ダンジョン・戦闘の項目: この作業は当てはまらない（中身を変えない）。
