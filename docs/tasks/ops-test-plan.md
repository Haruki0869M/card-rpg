# 運用テスト計画（改訂版）— DESTINY OF CRYSTALIA

作成: Claude（2026-11-09）。ChatGPT のレビューを受けて作り直した版。
**この文書はまだ計画だけです。テストの実行・ゲーム本体の変更はしていません。**

---

## 0. 結論（先に）

- 目的を「AIが遊んで楽しさを採点する」から、**「楽しさを邪魔する構造の問題を、証拠付きで見つける」**に変えます（レビューの指摘Aを採用）。1〜5点の採点はやめます。
- 調べて分かった一番大きなこと: **ゲームの中身（エンジン）は、画面なしで速く動かせます。** 状態の中に乱数の続き（`rngState`）が入っているので、**同じ場面を丸ごと写して、別々の手を試して比べる**ことができます。指摘B（選択の意味）は実現できます。
- ただし、比べるための道具（分岐比較ハーネス）は新しく作る必要があります。8時間の中で作れるのは**最小構成**までです（§3）。
- 自動で遊ぶ bot は「下手で単純」です（転職しない・お供を迎えない・報酬は先頭・手札は左から）。そのため **bot の勝ち負けをそのまま楽しさや難しさの根拠にはしません。**
- このテストで「楽しいと証明できた」とは言いません。分かるのは「楽しさを邪魔しそうな所の候補とその証拠」までです。

- 毒などの状態異常によるダメージに「誰から」が入っているか。

## 2. レビューの指摘への答え（STEP 1）

| 指摘 | 判定 | 理由・補足 |
|---|---|---|
| A 楽しさを直接測れない | **採用** | そのとおり。採点はやめ、「観測事実／仮説／人が確かめること」の3つに分ける |
| B 選択の意味を比べる | **採用（実現できる）** | 状態を写して分岐できる。**補足（反論ではなく注意）**: 分岐の後の乱数が手ごとにずれるので、「手の差」と「運の差」が混ざる。そこで、分岐した後の `rngState` を種を変えて N 回振り直し、**運のばらつきより手の差が大きいか**で判断する（ゲーム本体は変えず、テストの道具の中だけでやる） |
| C 難しいと理不尽を分ける | **採用** | `BattleEvent` で「全滅の直前に受けたダメージが、予告されていた行動からか」を数えられる見込み（§1の要確認） |
| D 侵食度・灯火・転職の関係 | **一部採用** | 寄り道・転職を比べるには、bot に「寄り道する」「転職する」動き方を足す必要がある。8時間では**寄り道の比較だけ**を「時間があれば」に入れ、転職は延期。気持ちの面は人が確かめる |
| E お供の評価 | **採用（ただし今ある物だけ）** | 今あるのは、出会い（お供の候補が出る出来事）・世界マップで後ろを付いてくる・撫でる・懐き度の見た目・お供の能力・戦闘のお供のボタン・うちの子図鑑。**無い交流は数えない** |
| F 協力の3つの形を分ける | **採用** | 「1人で全員」と「スマホを回して」は、画面の上では受け渡しの画面があるかの差だけ。物理的に渡す手間は人の確認に回す。オンラインはエミュレーターで別に測る |
| G 範囲が広すぎる | **採用（順番は一部反論）** | 絞るのに賛成。ただし「最初の15分」は**今ある道具で安く測れる**ので、順位は2番でも、**実行は最初**にする（道具づくりの待ち時間に回せる） |
| H 再現できる記録 | **採用** | ビルドの番号（`index-*.js` とコミット）・種・初期状態の保存データ（JSON）・命令の列を必ず残す。**スクリプトの失敗とゲームの不具合は分けて数え、失敗した回も集計から消さない** |
| 指標10個 | **一部採用** | 8時間で測るのは5つ（§4の★）。残りは測り方だけ決めて延期 |
| 5つのぶつかり合い | **一部採用** | ①③⑤は比較実験にできる。②は「時間があれば」。④（転職）は延期 |

## 3. 8時間でやること（STEP 2）

### 時間の割り振り

| 時間 | 内容 |
|---|---|
| 0:00–0:30 | 準備: §1の要確認3つ。ビルドの番号と種を決める |
| 0:30–1:30 | **T0・T1 の実行**（今ある画面の道具。待ち時間に道具づくり） |
| 0:30–3:30 | **分岐比較ハーネスを作る**（新しいテスト専用ファイル。ゲーム本体は変えない） |
| 3:30–6:00 | T2〜T5 の実行（重い処理は同時に2つまで。パソコンが弱いので、分岐の数を絞る） |
| 6:00–7:30 | 結果の整理・レポート |
| 7:30–8:00 | 予備（失敗した時のやり直し） |

**正直な見積もり**: 指標10個と5つのぶつかり合いを全部やるには、道具づくりだけで8時間を超えます。下の「必須」だけなら8時間に収まる見込みです。

| 段階 | テスト |

## 4. 指標の測り方（★＝今回測る）

数値の合格ラインは**決めません**（根拠が無いため）。数回〜数十回の試行なので、**「傾向の候補」**として書き、「統計的に確か」とは言いません。

| 指標 | 測り方 | 要るデータ | 測れない時 | 読み方・分からないこと |
|---|---|---|---|---|
| ★有効選択率 | 戦闘で手を選ぶ場面ごとに、選べる手（カード×狙い×フォーカスの有無）を全部試し、それぞれを N 回（種を変えて）戦闘の終わりまで bot で進める。**一番良い手と一番悪い手の差が、同じ手での運のばらつきより大きい場面の割合** | 状態の写し・`BattleEvent`（勝敗・残りHP・ターン数） | 手が多すぎる場面は、カードだけ（狙いは最も弱い敵）に絞る | 低い＝どれを選んでも同じになりやすい。**その差にプレイヤーが気づけるか**は分からない |
| ★カード選択の偏り | 上の比較で「一番良い手」になったカードの回数を数え、偏りの指数（各カードの割合の2乗の合計）を出す | 同上 | — | 高い＝決まった1枚ばかり。bot が使った回数は**左から使う癖**があるので使わない |
| ★運と判断の比べ（⑤） | 同じ場面で、①手ごとの結果の差 と ②同じ手での種による差 を比べる | 同上 | — | ②が①よりずっと大きい＝運が判断を打ち消している候補。**フォーカスを使った時に②がどれだけ縮むか**も見る |
| ★敗因の見えやすさ | 全滅した戦闘の最後の2ターンのダメージを、「予告されていた敵の行動から」「画面に出ていた状態異常から」「予告に無い物から」に分けて割合を出す | `BattleEvent`（damage の sourceId・enemyAct）と、その直前の敵の予告 | 予告が状態に残っていなければ、画面の自動操作で予告の文字を写真に残して照らし合わせる | 「予告に無い物」が多い＝理不尽に感じる候補。**負けて納得できるか**は人が確かめる |
| ★待ち時間の割合（③） | 協力の時、命令の1つごとに「その人が今できることがあるか」を記録し、**何もできない手の割合**を人ごとに出す。画面では敵の手番・演出の秒数も測る（`enemy-turn-timing.mjs` を流用） | 命令の列・その時の手番 | 「できることがあるか」を判定する関数が無ければ、bot が次に動かす人（`botNextCommand`）で代わりにする | 高い＝待つ時間が長い候補。**待つ間に楽しく見ていられるか**は人が確かめる |
| ★お供との接触 | 画面の道具で、世界マップ・町・ダンジョン・戦闘でお供が画面に出ている割合（一定間隔の写真）。画面なしで、最初のお供の候補が出るまでの手数、撫でられる機会、お供の能力の発動回数 | 写真・状態（お供の候補）・`BattleEvent`（ability） | — | **可愛いか・愛着が湧くか**は人が確かめる |
| 報酬がすぐ役に立つか（時間があれば） | カード・装備を手に入れてから、初めて使う（戦闘で出す・装備する）までの戦闘の数 | 命令の列と状態 | — | bot は報酬に先頭を選ぶので、偏りがある |
| 寄り道の代償（時間があれば） | 「まっすぐ進む bot」と「町と出来事に余分に寄る bot」で、ボスの時の侵食度・クリア・灯火の使い方を比べる | bot の動き方を1つ足す | — | 寄り道がいつも損＝探索やお供と過ごすのが損になる候補。**作者の意図の確認が要る（§8）** |
| ビルドの差（延期） | `k7survey` の結果を流用 | — | — | — |
| 逆転の可能性・復帰の負担（延期） | 不利な場面から、一番良い手を探す方法と bot の勝率の差／途中で読み込み直した時の画面の情報 | — | — | — |

## 5. テストケース一覧（STEP 3）

### T0 進めなくなる・データが消える・同期の崩れ（必須・自動・30分）
- **目的**: 遊べなくなる問題が無いかを最初に確かめる（仕様の合否）。
- **やり方**: 公開前の確認と同じ（vitest・画面の確認20本・7シナリオ×2人/4人の `adventure.mjs`・`online.mjs` をエミュレーターで）。
- **問題とする条件**: 止まる・保存が消える・端末の間で状態がずれる。
- **証拠**: 実行の記録・写真・保存データ。

### T1 最初の15分（必須・自動＋写真・60分）
- **目的**: 初めての人が最初の戦闘を終えるまでに、何をどれだけ読み・押すかを測る。
- **初期状態**: 何も保存されていない端末、390×844、「やさしい」、1人。
- **手順**: タイトル → 新しい冒険 → キャラ作成 → 出発 → 最初の戦闘の勝利まで。新しい「はじめての案内」はON。
- **測る物**: タップの数・かかった時間・画面に出た文の文字数・初めて出てくる言葉の数（用語集の言葉と照らし合わせる）・案内が進んだ順番。
- **期待**: 案内の3段が順に出て、迷う所（押せる所が無い画面）が無い。
- **問題とする条件**: 押せる所が分からない画面がある／最初の戦闘までに、説明の無い言葉が多く出る。
- **証拠**: 動画・写真・数え上げの表。
- **合否と仮説を分ける**: 「止まる」は合否、「言葉が多い」は仮説。

### T2 戦闘の選択の意味（＋⑤ 運と判断）（必須・画面なし・道具づくり3時間＋実行90分）
- **目的**: 手の違いで結果が変わるか。運が判断を打ち消していないか。
- **前提**: 分岐比較ハーネス（§6）。
- **初期状態**: 3つの場面を固定の種で作る ①最初のダンジョンの普通の戦闘（2人）②ボス戦（2人）③不利な場面（HPが半分以下）。ジョブは最初の2つの組み合わせ。
- **手順**: 各場面で、味方の最初の3手それぞれについて、選べる手を全部試し、1つの手につき種を変えて N 回（パソコンの負荷を見て N=10〜20）戦闘の終わりまで進める。
- **測る物**: 有効選択率・カード選択の偏り・運と判断の比べ・フォーカスを使った時の差・連携を狙った時の差。
- **問題とする条件（仮説）**: 手の差が運の差よりいつも小さい／1枚のカードが常に一番良い／連携を狙う手がいつも一番良い（集中攻撃しか選べない）。
- **証拠**: 場面の保存データ・命令の列・結果の表（JSON と md）。

### T3 協力の待ち時間（＋③）（必須・画面なし＋画面・60分）
- **目的**: 協力の時に、何もできない時間がどれくらいあるか。
- **条件を分ける**: ①1人で全員（画面なし）②スマホを回して（画面。受け渡しの画面の回数と秒数）③オンライン2台（エミュレーター）。
- **測る物**: 人ごとの「何もできない手」の割合・敵の手番の演出の秒数・受け渡しの画面の回数。
- **人が確かめる物**: 実際に渡す手間・待つ間に相談したくなるか。

### T4 負けた理由が見えるか（必須・画面なし・45分）
- **目的**: 全滅の直前のダメージが、画面で予告されていた物かどうか。
- **初期状態**: 「ふつう」の2人で、全滅が出るまで固定の種を何本か回す（全滅を作るため、わざと下手な bot のまま）。
- **測る物**: 敗因の見えやすさ（3分類の割合）。予告に無かったダメージの中身の一覧。
- **問題とする条件（仮説）**: 予告に無いダメージが全滅の大きな原因になっている。
- **注意**: **難易度の数値は変えない。** 直す案は「情報の出し方」に限って出す。

### T5 お供の存在感（必須・画面＋画面なし・45分）
- **目的**: お供がどれくらい画面に出て、関わる機会があるか。
- **手順**: 画面の道具で、お供を迎えた状態の保存データから、世界マップ10歩・町・ダンジョン・戦闘1回を遊び、1秒ごとに写真。画面なしで、7シナリオ×数本で、最初のお供の候補が出るまでの手数。
- **測る物**: お供との接触（表示の割合・撫でる機会・能力の発動の回数）。
- **人が確かめる物**: 可愛さ・愛着。**無い交流機能は「無い」と書く。**

### T6 寄り道の代償（＋②）（時間があれば・画面なし・60分）
- 「まっすぐ」と「寄り道する」の bot の2つで、ボスの時の侵食度・クリア・灯火を比べる。**作者の意図の確認が先（§8の問い2）。**

### T7 報酬がすぐ役に立つか（時間があれば・画面なし・30分）
- 手に入れてから初めて使うまでの戦闘の数。

## 6. 自動テストの作り方（STEP 4）

- **ゲーム本体は変えません。** 新しく足すのはテスト専用の物だけです。
  - `src/engine/__tests__/opsBranch.sim.test.ts`（仮の名前）: `k7survey.sim.test.ts` と同じく、環境変数（例: `OPSSIM=branch`）を付けた時だけ動く。普段のテストには入れない。
  - 中身: ①固定の種で場面を作る ②状態を写す（`structuredClone`）③選べる手を並べる ④手ごとに `rngState` を振り直して bot で戦闘の終わりまで進める ⑤結果を `screenshots/ops/*.json`・`*.md` に書く。
  - 「選べる手を並べる」関数がエンジンにあるかは**まだ確かめていません**。無い場合は、手札×狙える相手×フォーカス0/最大を、テストの中で組み立てます（ゲームが拒む手は、エラーで分かるので外す）。
- **乱数**: `Math.random` は使いません。種はテストの中で決めて記録します。
- **画面の道具**: `scripts/lib.mjs` の共通の手順と、`scripts/gemini-verify/rec.mjs`（録画）を流用します。T1 用の数え上げのスクリプトを1本足します（`scripts/ops-first15.mjs`、仮の名前）。
- **パソコンの負荷**: 重い処理は `heavy.mjs` で同時に2つまで。T2 は試す手の数×N回なので、最初に小さく回して時間を測ってから、N を決めます。
- **ゲーム本体の変更が要るかもしれない所**: §1の要確認で、敗因のデータ（ダメージの「誰から」）が足りなかった場合。**その時は勝手に足さず、作者に聞きます。**

## 8. 「プレイヤーに一番してほしい行動」についての考え（設計者として）

**私の考え（作者の確認が必要な案）**
> 仲間（とお供）と一緒に、限られた手札とスロットの運の中で「今いちばん良い一手」を探し、ぎりぎりで勝ち抜くこと。

**それぞれの仕組みが、この行動を後押ししているか（仮説）**

| 仕組み | 後押し | 邪魔しているかもしれない所（仮説） |
|---|---|---|
| 戦闘（スロット・フォーカス） | ★フォーカスは「運に対して判断で勝つ」道具 | 運の幅が大きすぎると、判断の意味が薄れる（T2⑤で確かめる） |
| 連携＋20% | 仲間と相談する理由になる | 「同じ敵を殴る」が常に正解だと、相談ではなく決まり事になる（T2） |
| 協力 | 一緒に決める楽しさ | 待ち時間が長いとテンポが落ちる（T3） |
| 探索・町 | 準備と発見 | 侵食度が上がるので、寄り道がいつも損なら、探索を楽しむ気持ちとぶつかる（T6） |
| お供 | 愛着。懐き度で強さが変わらない作り＝「可愛がる義務が無い」良さ | 戦闘や探索の中での存在感が薄いと、愛着がつく機会が少ない（T5） |
| 侵食度 | 「いつ何をするか」を選ぶ緊張 | 上と同じ |
| 命の灯火 | 負けても続けられる安心と緊張 | 残りが少ないと、新しいジョブや戦い方を試すのを控えてしまう |
| 転職 | 長い目で見たビルドの楽しさ | Lv1に戻る損の感じが、育てる楽しさより強く出るかもしれない（今回は延期、人が確かめる） |

**作者の答え（2026-11-09）**
1. 一番してほしい行動は、上の案で**合っている**。
2. 寄り道は「**得がある時もある**」くらいで良い。いつも得とは限らないのがゲーム。→ T6 では「寄り道がいつも損になっていないか（得をする回が一度も無い、になっていないか）」を見る。「いつも得」を目指す改善案は出さない。
3. 大事にする遊ぶ形は「**1人で全員**」と「**オンライン**」の両方。→ T3 はこの2つを深く見る。「スマホを回して」は確認を軽くする。
4. 転職で Lv1 に戻るのは**狙いどおり**（ほかの有名なRPGでも同じ形が多く、しっくりくる）。→ Lv1 に戻ること自体は問題として扱わない。転職のテストは延期のまま。

## 9. Android 2台で遊ぶ時の確認リスト（STEP 6・作者とパートナー向け）

遊んだ後に、2人それぞれ「はい・どちらでもない・いいえ」と、ひとことで答えてください。

1. 説明を読まなくても、何を押せばいいか分かりましたか？
2. 文字やボタンは、見やすく押しやすかったですか？（片手で遊べましたか？）
3. 戦闘で「どのカードにしよう」と迷う場面はありましたか？ その迷いは楽しかったですか？
4. 負けた時、「なぜ負けたか」が分かって、納得できましたか？
5. お供を可愛いと思いましたか？ 名前を付けたくなりましたか？
6. 戦闘の途中で、相手と相談したくなりましたか？
7. 相手の番を待つ時間は、退屈でしたか？
8. 侵食度が気になって、寄り道をやめたことはありましたか？
9. 一番楽しかった場面と、一番いやだった場面はどこですか？
10. また遊びたいと思いますか？ それはなぜですか？

## 10. このテストで分かること・分からないこと

- **分かること**: 手の違いが結果に出るか、運が判断を打ち消していないか、負けの原因が予告されていたか、協力の時の待ち時間、お供が画面に出る量、最初の15分の手間。どれも「候補と証拠」として。
- **分からないこと**: 実際に楽しいか、可愛いと思うか、負けて納得できるか、また遊びたいか。これは §9 で人が確かめます。
- **やらないこと**: 難易度やゲームの仕様を勝手に変えること。「楽しいと証明できた」と言うこと。
