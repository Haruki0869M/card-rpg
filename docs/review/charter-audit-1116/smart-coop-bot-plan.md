## 0. 結論（先に）

**「直してから実装」＋「オーナーに聞く事が、計画の3つのほかに2つある」。** 作り直しは要りません。計画の骨は正しく、抜き打ちした事実 13個は全部コードと合っていました（行番号の1行ずれが1つだけ）。憲章に反する所はありません（ゲームの数字・中身を変えない／bot が勝つ事を合格にしない）。

実装の前に計画へ書き足す物（重い順。くわしくは §3）:

1. **センサーの「わざと壊した版」での確かめが無い**（今は、小さな HTML の自己テストだけ）。直す前の不具合を戻した版で bot が本当に検出できる事を、区切り1と3の「できた」の線に入れる。
2. **フォーカスの確かめ（S5）の `data-check-chance` は、今の作りでは「本当に使われた成功率」を出せない**（エンジンの結果に成功率が入っていない）。確かめ方を変える。
3. **「同時に押す」を1度も試さない計画**（いつも1台ずつ・全端末が落ち着いてから）。人のすれ違いで一番起きやすい形なので、揺さぶりに足す。
4. **「失敗の後も続ける」の続け方が決まっていない**（かぶさって押せない時に、どうやって先へ進むか）。裏から押して続ける道を、はっきり禁止する。
5. **本番に書かない守りを、通信の層にも1つ足す**（今の守りは台本の URL の字を見るだけ）。
6. **「エミュレーターの時だけ読まれる」は正しくない**（`?debug` でも読まれる。`src/main.tsx:22`）。`&seed=` の門は `emulatorFromUrl()` で作る、と明記する。`src/net/room.ts` は**触らずに作れる**ので「触らない」と書く。
7. **端末を「閉じて開き直す」と別の人になる**（匿名ログインは端末ごと）。同じ context のまま、1台ずつ、に直す。
8. 作業の分け方: `view.mjs`・`content.mjs` を 2-Sa と 2-Sb が両方触る（重なる）。
9. 「bot が見逃す物」の正直な一覧が、計画に無い（§3-9 に案）。

## 3. 見つけた事（重い順）と直し方の案

### 3-1.【重い】センサーが「本物の不具合」を検出できるかの確かめが無い
- 今の計画: `selftest.mjs`（ゲーム無しの小さな HTML）と、通しの中の「名前つきの確かめ」。どちらも「直した後の版で OK が出る」だけで、**直す前に戻した時に NG が出るか**を見ていない。これが無いと「何も見つけない bot」と「不具合が無い」が区別できない。
- 案: 別のフォルダ（worktree。正本のフォルダは触らない・コミットしない）に、印の入った今の版から**直しのコミットだけを戻した版**を作り、別のポートで配って bot を当てる。
  - 区切り1: 実機の不具合②（待ち中のシートの潰れ・かぶさり。直し = `2b5b0f7`）。場面を用意して、センサーが当たる事。
  - 区切り3: 実機の不具合①（フォーカスが0で上書き。直し = `35ffa1b`）と、祠の行き止まり（直し = `184d947`）。S5 と「互いに待つ」の検出が当たる事。
  - きれいに戻せない時は、その不具合の形を小さく入れ直した版でも良い（何を入れたかを報告に書く）。
- 「できた」の線に「壊した版で NG・今の版で OK」を足す。

### 3-2.【重い】S5 の `data-check-chance`（使った成功率）は、今の作りでは本当の値にならない
- イベントの結果は `{ optionIndex, heroId, results, success, text, loot }` で、**成功率は入っていない**（`src/types/game.ts:489`・`src/engine/game/game.ts:1357`）。結果の所に足す `data-check-chance` は、画面が後から計算し直した値になり、「その値で判定された」証拠にならない。エンジンの結果に成功率を足すと、保存と状態の印が変わるので、してはいけない。
- 案（ゲームの動きを変えない確かめ方）:
  1. 押す前: 挑む段の成功率の字が、フォーカスを足すと上がる（今の画面の字。`CheckPanel`）。
  2. 押した後: 結果の枠の並び（`results` の `'focus'` の数 = 画面の星の枠）が、足した数と同じ。これはエンジンが出した本物。
  3. 挑む役のフォーカスが、その数だけ減る・ほかの人は減らない（全端末で）。
  4. 審判が、状態の写し（読むだけ）でも 2 と 3 を照らす。
- B7 は `data-check-result`・`data-check-focus`（= `results` の中の focus の数）だけにし、`data-check-chance` はやめる。

### 3-3.【重い】「同時に押す」を試さない
- `conductor.mjs` は「いつも1台ずつ・全端末の番号がそろってから」。再現しやすさのためには正しいが、2人が同じ瞬間に票を入れる・片方の操作が届く前にもう片方が押す、という**人のすれ違いの本体**を1度も通らない。
- 案: 揺さぶりに「S13 同時押し」を足す（票・開け役・準備完了・取り合いで、2台が同じ瞬間にタップ）。確かめは「止まらない・状態の印がそろう・票が消えない」。この時だけは操作の記録の順が毎回同じでなくて良い、と決める。

### 3-4.【重い】失敗の後の「続け方」が未定
- かぶさって押せない・窓が潰れて要るボタンが無い、の後は、画面の操作では進めない事が多い。計画は「進められる限り続ける」だけ。
- 案: 続けるのは**画面の操作で進める時だけ**（別の道・シートを閉じる・読み込み直し）。進めない時は、その通しをそこで終え、次の節目の保存から「場面から」で続ける（差し込みを使った事を報告に書く）。**スクリプトで無理に押して続けるのは禁止**、と計画に書く。

### 3-5.【重い】本番に書かない守りを通信の層にも
- 今の守り: 台本の URL に本番の名前があれば止まる（`coop-agree.mjs:17`）＋ `?emu=` が無ければ止まる。どちらも**台本が開く URL の字**を見るだけ。
- 読んで確かめた事: `?emu` が URL にあれば、つなぐ先は必ずエミュレーター（`firebaseBackend.ts:122-129`）。URL の `?` 以降を書き換えるコードは無い（`history.pushState` は URL を変えない。`useBackButton.ts:16`）。読み込み直し・「前の部屋に戻る」（画面の中で戻る。`TitleScreen.tsx:48`）・合言葉の手打ち・「場面から」のどれも `?emu` は残る。**今の道では本番に届かない。**
- それでも、`?emu` が落ちた URL を1度でも開けば、手元のビルドは本番の設定でつなぐ。案（足す守り2つ・どちらも軽い）:
  1. ブラウザを「127.0.0.1 と localhost 以外は名前を引けない」設定で起こす（Chromium の `--host-resolver-rules`）。本番へは物理的に届かない。
  2. 審判が、画面を読むたびに、その端末の URL に `emu=` がある事を見る（無ければ即止める）。
- `online.mjs` の `REAL`（本番に当てる道）は、新しい bot に**持ち込まない**と書く。

### 3-6.【中】確認用の入口の説明と、`room.ts`
- `onlineDebug.ts` は `?emu` **か `?debug`** で読まれる（`src/main.tsx:22`）。本番でも `?debug` を付ければ `window.__online` は出る（今もそう）。`resyncLog()` は読むだけなので害は無いが、計画の「エミュレーターの時だけ」は直す。
- `&seed=` の門は「`onlineDebug` が読まれたか」ではなく、**`emulatorFromUrl()`（`src/net/onlineEnv.ts:6`）が値を返す時だけ**にする。`?emu` がある時はつなぐ先が必ずエミュレーターなので、本番の部屋の種は決められない。テスト: `?emu` 無し・`?debug` だけ、の両方で種が使われない事。
- **`src/net/room.ts` は触らずに作れる**: 種は `start(seed = …)` の引数がもうある（`room.ts:574`）。取り直しの記録は `room.on()`（`room.ts:256`）で `type: 'resync'` を聞けば、`onlineDebug.ts` の中だけで作れる。計画の 1-G の触るファイルに `room.ts` は無いが、「触らない」と明記する（11/15 に通信の直し `d940357`・`c567b9e` が入った所）。
- 取り直しの記録は、ページを読み込み直すと消える。読み込み直しの直前に審判が読んで残す。読み込み直しの後は理由が `'join'` か `'start'` になる（`room.ts:359,389,691`）ので、計画の除き方で合う。
- 触ってはいけない物（`vite.config.ts`・`package-lock.json`・`firebase.json`・`database.rules.json`・`src/net/firebaseConfig.ts`）は、計画のどの区切りにも出てこない。良い。Playwright は今の入れ方のまま使う（新しい package を足さない）と1行書く。

### 3-7.【中】端末を閉じて開き直すと、別の人になる
- 細 §8-1「節目ごとに端末を閉じて開き直す（読み込み直しの揺さぶりを兼ねる）」。ログインは匿名（`firebaseBackend.ts:131`）で、context を捨てると別の人になり、自分の席に戻れない。全員を同時に閉じると「部屋にだれもいない」形になり、S7・S8（1台ずつ）とは別の事を試してしまう。
- 案: 同じ context のまま、ページだけを1台ずつ読み込み直す。メモリを捨てるための開き直しは、「場面から」と同じ手順（新しい部屋＋節目の保存）で区間を分ける時だけ。
- S8 の「ホストが代わらない」は時間しだい（PC が重いと代わる）。合否は「状態の印が同じ・続けられる」にし、ホストが代わったかは記録にする。

### 3-8.【中】印の決まりに足す物（プレイヤーに見える物・動きを変えないために）
- **見えない情報を印に出さない**（霧の中・隠れた予告・開ける前の箱の中身）。B3 には「隠れている時は ?」とあるが、全部の印の決まりにする。A7 は「見えたマスだけ」の今の層（`LandscapeLayer.tsx:405`）に足すので合う。
- **印の値は、画面の字と同じ元から出す。** `view.mjs` は、字で出ている数字（HP・成功率・フォーカス）は字も読み、印と違えば「画面の字と中身のずれ」として報告する。印だけを読むと、字が古い・間違っている不具合を見逃す。
- A1（いちばん外に `data-mode`・`data-scene`）: `App` が場面の状態を新しく見るようになると、場面が変わるたびに全体を描き直す。動きは同じでも重さが変わるので、今 `App` が見ている値だけで作るか、作業者が描き直しの回数が増えない事を確かめる。
- A7 の `data-tide`（今の潮で変わる値）は、潮が変わるたびに 600 マスを書き直す。**変わらない印**（潮のマスかどうか）だけにし、今の潮は今ある `data-tide-icon` で読む。
- 1-G・2-G の線「今の確認が前と同じ結果」は良い。印は本番にも入る（見えない・大きさはごくわずか）事を、オーナーへの説明に1行。

### 3-9.【中】「bot が見逃す物」を計画に正直に書く（今は無い）
計画に、次の一覧を足してください。オーナーが「bot が通った = 実機も大丈夫」と受け取らないために要ります。
- 見た目: 少しのずれ・読みにくさ・色・絵と字の重なりのうち押せる物・演出の気持ちよさ・手ざわり・音。
- 絵とボタンの一致（憲章3の「扉の数・位置」）・字の中身の間違い（印が合っていれば通る）。
- 指の動き: 地図のドラッグ・つまんで拡大・長押し・**指でスクロールできるか**（bot はスクリプトで送る）。→ 1回の通しで、地図のドラッグと、シートの指のスクロールを1回ずつ本物のタッチで通すと、少し埋まる。
- 本物のスマホ: LINE の中のブラウザ（上下の帯で高さが変わる・キーボード・画面を離れて戻る）・本物の回線の遅れと切れ・電池の節約で止まる。390×540 は「形」をまねるだけ。
- 同時押し（§3-3 を足しても、全部の組み合わせは通らない）・3台以上が同時に読み込み直す形。
- 「やさしい」以外の難しさ・1台で遊ぶ時・ローカル協力（今の `adventure.mjs` などで見る）。
- bot の作戦が人と違う所（人ならやる変な順番の操作）。

### 3-10.【中】「最後まで遊ぶ」「完走」の言葉をそろえる
- 合格の線に「**エンディングまでの全部の区間を、通しか、節目の保存からの続きで、画面のボタンで遊んだ**」を足す。手で書き換えた保存（鍵を全部持たせる など）だけでエンディングを見た時は「完走」と呼ばず、報告に「通しで着いた所・続きで着いた所・書き換えで見た所」を分けて書く。
- オーナーへの完了報告は、この3つを分けて言う。

### 3-11.【軽い】開け役は bot も自分で計算する

### 3-12.【軽い・オーナーに伝える】センサーの読み替え3つ

### 3-13.【中】時間と運用
- 見立て（2人 1.5〜2.5時間・4人 3〜5時間・1本 5〜8時間・7本 35〜55時間）は、どれも【未確認】と書いてあり正直。点検役の見方: 1手 0.6〜1.0秒は、4台で毎回「全端末の画面を読む＋番号がそろうのを待つ」が入るので **4人は足りない見込み**（1.5〜3秒）。上限（2人 180分・4人 300分）は見立ての上の端と同じで、**時間切れが先に来やすい**。区切り 1-J で測った値で上限を決め直す、と書く。

### 3-14.【軽い】「バランスの崩れ」の報告
- 今は「おかしく見えたら書く」。何を「おかしい」とするかが無いと、毎回ばらつく。数字は動かさず、**記録の項目を決める**: 戦闘の数（憲章の 32〜40 と並べる）・戦闘ごとのターン数と減った HP・全滅した場所と敵・転職した時期（何戦目。憲章6の3幕と並べる）・寄り道の数・終わりの侵食度・1ターンで倒れた回数・使われなかった薬。判断はオーナー。

### 3-15.【軽い】作業の分け方
